# Private PDF OCR and page geometry

The opt-in `./docker-ocr` adapter rasterizes clean purpose-authorized PDF evidence and applies the fixed English Tesseract language pack. It returns source revision/hash, immutable image ID, exact worker-output hash, text hash, ordered pages and word boxes with confidence. Coordinates are pixels from the top-left of each rasterized page, with page width/height included; they are not PDF points. Layout records block/paragraph/line identifiers as machine estimates. Confidence is the engine's score divided by 100, not a calibrated probability of truth. Blank pages remain explicit.

OCR is always a derivative interpretation, never a replacement for the source or a factual verification. Every result warns that quotations require comparison with the source image. Poor scans, handwriting, rotated text, complex reading order and languages outside the installed pack may produce errors. No OCR quality benchmark or multilingual acceptance is claimed. The current fixed profile supports 1-10 pages, at most 2000 pixels on either axis, 10000 words and 8 MiB of output. Lower host page/word limits reject the result; the fixed worker may perform up to its own hard limits before that rejection. It does not silently return truncated success.

`containers/pdf-ocr` uses Poppler to rasterize each page separately, then Tesseract TSV output and a standard-library Python worker. The host strictly validates the output schema, contiguous page identities, coordinate containment, confidence, word count and UTF-8. Untrusted text is not interpreted as markup, commands or authority. The adapter uses the same factored runtime as PDF text extraction, retaining its scope, scan, purpose, exact-byte, immutable-image, capability and cleanup gates. OCR raises the fixed memory/swap allowance to 512 MiB and temporary storage to 32 MiB. Network/IPC remain disabled, the root filesystem read-only, the user unprivileged, capabilities dropped, no-new-privileges enabled, and CPU/process/file/output limits retained. Both host and in-container deadlines apply. See PDF_RUNTIME.md for daemon trust, plaintext temporary storage, shared-kernel, host-crash reconciliation and mutable build supply-chain limits.

No image pull occurs while processing. Build and review the OCR Dockerfile in a trusted pipeline and provide its immutable local image ID. `npm run test:docker:ocr` requires `DMP_OCR_TEST_IMAGE` and runs actual image-only PDF extraction and malformed-PDF rejection/cleanup; absent configuration fails. Ordinary local tests use schema/profile/gate checks. A native worker check using a benign fictional scan verifies algorithm behavior only and establishes no isolation acceptance. Local Docker is unavailable on the current development host; actual container qualification must come from CI and deployment tests.

The SDK's existing `./docker-pdf` export retains its behavior. Both adapters now use an internal shared runner, so CI must also pass the original embedded-text container tests. No durable job queue, transcription, translation, publication or live private-document processing is added.

Primary output-format reference: [Tesseract TSV documentation](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html#tsv-output). Build versions are recorded by the immutable image identity; reproducible/signed image supply chain remains deployment work.
