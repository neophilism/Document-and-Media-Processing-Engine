# Current Identity membership for private reconciliation

`createIdentityReconciliationHandler(jobs, outputs, membership, sessions, policy, clock)` from `./identity-reconciliation-http` composes accepted Identity PR10 with the existing Processing HTTP handler. The Identity package is pinned at `43bcccfba577114f51954f868906280ed7b7ba56`. This is opt-in; the older host-authenticated handler stays available.

The trusted session provider independently authenticates a HUMAN and returns only actorId/requestId/session-bound CSRF (or null). Fixed tenant/project/purpose/origin and Identity action `admin` are constructed from captured Processing policy. Current stored enabled human-owner authority is resolved in the Identity-owned database on EVERY session or reconciliation request. Provider-supplied roles/scope/kind cannot elevate a principal. Processing still checks its own fixed manager list, purpose, Origin/Fetch Metadata, CSRF, exact input and domain/output authority. A current owner is not automatically a listed Processing manager.

Only the existing GET /processing/session and POST /processing/reconcile routes exist. POST captures bounded body bytes BEFORE fresh session/membership authentication; a stalled body cannot retain an earlier session's roles. There are no execution, grant, identity-admin, retry, no-output, cleanup, object-download, send or publication routes. Exact existing-output reconciliation and its conservative acknowledgements are unchanged.

Identity and Processing MUST use separate operational databases and restricted logins. The wrapper receives the public Identity registry, never its database or keys. Jobs and outputs still share the Processing-owned database/private object root. Shared persistence SDK pin remains unchanged. The host must configure trustworthy clocks in both registries/services, current manager policy, session proofing, unpredictable session-bound CSRF, TLS/secure cookies/proxy/CSP and rate/connection/driver limits. No listening login service is supplied.

Membership verification and Processing changes happen in separate transactions/databases. A returned authorization snapshot is historical: revocation AFTER that check is not atomically fenced across Processing effects. Capability tokens/revocations are not checked by this role-based session adapter. Use separate current policy at effect boundaries; this wrapper is not a one-shot permit or distributed transaction. Do not reuse returned Contexts. Provider cancellation cannot undo side effects. Owning Identity SQL is awaited internally, but the consuming HTTP auth deadline can return before a noncooperative provider/Identity transaction finishes; the work may continue and its late result is fenced. Host query limits remain mandatory. HTTP408/503 do not prove rollback of any begun mutation.
