# Private PDF embedded-text runtime

`DockerPdfTextProcessor` is an opt-in server adapter for clean, purpose-authorized exact-byte PDF evidence. The trusted gateway supplies the source edition, hash and scan/permission results. These fields are not authentication and must never be accepted directly from an intake form. This adapter extracts embedded text with page separators and provenance. The separate OCR/page geometry adapter is described in OCR_RUNTIME.md. Speech recognition and translation remain pending. Both adapters use the same internal runner with distinct fixed resource profiles.

Use a dedicated Linux processing host with Docker and kernel-enforced memory, swap, CPU, PID and seccomp controls. The adapter checks the daemon report and fails closed when these controls are unavailable. Configure an immutable locally installed `sha256:` image ID, never a tag. It never pulls images during processing. Build the supplied Dockerfile in a trusted build pipeline, review its dependencies and record the resulting image ID. The current build base and package repositories are mutable: this is not a reproducible-build or signed supply-chain acceptance claim.

The fixed profile uses a non-root user, no network or IPC, a read-only root filesystem, dropped capabilities, no new privileges, bounded temporary storage, CPU/memory/process/file limits, disabled container logs and a read-only input mount. Arguments do not pass through a shell. Docker receives a private empty configuration and no inherited application credentials. A 20-second in-container deadline complements the configurable host timeout. Output and diagnostics are bounded; raw parser diagnostics are not exposed through domain errors.

Processing creates a temporary plaintext copy of the already-authorized PDF. Use encrypted ephemeral storage on a restricted host. This is not end-to-end encrypted processing or protection from a privileged Docker daemon/host administrator. Containers share the host kernel; high-risk deployments may require a stronger VM isolation boundary. Deleting temporary files is not a secure-erasure guarantee.

The adapter removes its own uniquely named container and input directory after success or failure. `parser_cleanup_failed` identifies the random container name requiring operator reconciliation; stop further dispatch until the host is reconciled. A host crash can interrupt cleanup: deployment startup and periodic reconciliation must remove stale containers with the `accountability.processing.run` label and stale private work directories before accepting new sensitive work. The in-container deadline bounds parser execution but does not itself delete a stranded container. No automatic global sweeper is implemented here.

Run `npm run check` for local unit/process tests. For actual isolation integration, build the Dockerfile, set `DMP_TEST_IMAGE` to the resulting image ID, then run `npm run test:docker`. The integration command fails without its required image; it never silently substitutes a fake runtime. CI builds the image and requires successful extraction and malformed-input rejection with container cleanup. Local development without Docker does not establish runtime acceptance.

Primary runtime references: [Docker container run](https://docs.docker.com/reference/cli/docker/container/run/) and [resource constraints](https://docs.docker.com/engine/containers/resource_constraints/). Resource controls depend on the host kernel and daemon, which is why capability checks are mandatory.
