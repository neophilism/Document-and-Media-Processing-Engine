# Processing-owned private text outputs

`./text-outputs` exports `PrivateTextOutputs` over the stable Evidence SQL SDK and `PrivateObjectStore`, using this engine's operational database and a separate Processing-owned encrypted object root. It never reads another engine's database or object root. Trusted host configuration supplies current manager/worker lists, a live clock, a mandatory current output-policy callback and a mandatory current source reader (the accepted authenticated Evidence source adapter can supply it).

`storePrivateText` fits the accepted worker callback. It requires the actual consumed edition in the ledger, original scoped worker identity/purpose and a live execution window. It captures derivative input before awaits, independently re-reads the source and recomputes the accepted UTF8 extraction. Exact source/processor/language/output hash and UTF8 byte length must agree; a worker-supplied output hash alone is not proof. Raw text stays out of SQL metadata and travels to the private encrypted object store only.

A deterministic intent is durably staged before blob writes. Private artifact metadata and a separate exact receipt record commit atomically with intent completion and outbox after encrypted write/readback and fresh policy/clock checks. Artifact and receipt references are actual immutable SQL records at revision 1, not invented editions. Repeated exact storage cannot produce a second edition; conflicting metadata fails closed. SQL and filesystem effects are not one atomic transaction: rollback/crash can leave a pending intent and private object. Pending state never certifies no output, never permits execution retry and is not returned as a committed outcome. Explicit pending finalization is described below; safe orphan cleanup remains separate work.

`verifyOutcome` and explicit `recoverOutcome` recheck current listed authority and policy, the consumed history and exact private records, independently re-read authorized source bytes/recompute extraction, and decrypt/re-hash the persisted output. They expose outcome references, not a plaintext download API. Recovery can confirm a committed outcome after a lost acknowledgement, including after lease expiry; it does not rewrite blobs or run a processor job again. Verification may deny if current source policy changes. Checks across source services/SQL/filesystem are not a distributed atomic permission fence, and no persistent receipt/liveness attestation or external audit anchor is claimed.

Callbacks are bounded/cancellable; begun SQL/local filesystem work is awaited and may outlive caller cancellation. A late storage write can leave a pending object. Host contexts, key custody, object-root ownership, local filesystem availability, current policy refresh and deployment isolation remain mandatory. Construction captures identity lists; recreate the instance after configuration changes. No public policy switch, send, publication, daemon, retry or no-output settlement is exposed.

Eight new groups use actual restricted migrated PGlite and real temporary encrypted objects with controlled source/policy callbacks. They do not qualify deployed keys/storage/identity/source gateways, network-session output contention or crash/power-loss recovery. Groups cover exact lifecycle and scopes, forged text, object tampering, current policy/source denial, lost acknowledgement, post-outbox rollback with retained pending bytes, verification deadlines/cancellation/expiry and immutable captured inputs. Final-head CI is recorded in the PR.

Wire methods with their instance receiver, for example `storePrivateText: outputs.storePrivateText.bind(outputs)` and `verifyOutcome: outputs.verifyOutcome.bind(outputs)`. The source callback is mandatory for independent extraction checks; hashing metadata alone is insufficient. No-output settlement services must consider all pending and committed intents/objects and establish stopped/quiescent execution; this module supplies no no-output or liveness proof. Lack of a receipt is not evidence of absent output.

Policy and source callbacks sample the trusted clock again on each verification stage, including recovery after the execution lease expires; an old request timestamp is not reused as current policy time. The caller still supplies authenticated identity context.

## Explicit pending finalization

`finalizePending(context, jobId, consumedRevision, signal)` requires a currently listed human owner manager and the exact consumed job/intent edition. It independently rereads the authorized source, recomputes UTF8 extraction and authenticates existing encrypted output bytes using the configured Processing-owned root/key. The constructed object candidate is not proof until authenticated decryption, hash and size checks pass. Missing, corrupt or unavailable-key objects deny finalization; the method never writes an object, executes a processor, settles no-output or queues a retry.

Finalization may occur after the execution lease expires because it only publishes already-existing independently verified content. It repeats current policy checks and serializes exact intent/artifact/receipt/outbox publication under the ledger project lock. The job stays consumed until separate verified completion. An already-stored outcome replays through current independent verification, including after completion. Publication can race a late normal writer conservatively; immutable expected-zero records and the same intent prevent a second edition. No stopped/quiescent execution claim is made.
