# Durable text-processing job ledger

`./text-jobs` uses the pinned Evidence SQL SDK in a dedicated processing operational database, never the Evidence engine database. Listed human managers submit exact text jobs or cancel unconsumed work. Listed service/agent workers obtain a purpose-bound lease and separately consume it before I/O. Expired unconsumed work can be re-leased with a new revision. Consumed work never becomes eligible again merely because a lease expires.

Consumption is deliberately not idempotently replayed as another permit. If the commit acknowledgement is lost, read current state and reconcile; do not execute from a read snapshot or call a processor based on a cached lease. Managers cannot recall consumed effects. Completion requires a mandatory bounded trusted outcome verifier and binds an exact derivative edition/hash and receipt edition; outcome and audit/outbox commit together. No source bytes, credentials, model output or model reasoning are stored in the queue.

The mandatory start verifier must establish current clean scan status, source bytes/hash/length, purpose authorization and source access. The mandatory outcome verifier must establish that the exact source/job profile produced the exact private derivative and that the receipt is authoritative. Neither callback may infer authority from caller strings or public availability. Host assertions are not authentication. Database state is scoped and immutable by revision; external permission verification is not an atomic fence across another service or processor.

This is queue/permit/outcome orchestration for the accepted UTF8 text processor only, not a daemon, byte fetcher, object store or processor runtime. A real worker must consume before acquiring bytes/performing I/O, call the existing exact-byte processor and store a private derivative/receipt through qualified services. Callback timeouts stop waiting, not callback side effects. Costs, quality, OCR/model dispatch, cancellation signals into running processors and deployment acceptance remain pending. Specific network-session ledger scenarios are tested in disposable PostgreSQL CI; see POSTGRES_TESTS.md. Source purpose/clock/context and manager/worker identity must be supplied by trusted host authentication. A job snapshot is not an authentication credential.

Ten new integration groups use actual pinned migrations and a restricted PGlite login. They cover lifecycle/replay, lost consumption/completion acknowledgements, expiry/re-leasing, scope/purpose, bounded verifiers, authorization-time cancellation/expiry, simultaneous consumption and post-insert transaction rollback. They do not qualify independent database network sessions or live services; final-head CI is recorded separately in the PR.

The constructor also requires a trusted live clock function. Consumption samples that clock inside the final transaction after authorization and acquisition of the SDK project serialization lock, and refuses an expired lease or clock regression relative to the authenticated request time. `consumedAt` stores that sample. Audit timestamps otherwise retain authenticated request context and are not independent wall-clock attestations.

The host must replace a registry instance when deployment identity lists change; each instance captures its policy. Listed workers can read jobs in the same authorized project/purpose; this is not a finer case compartment system. Verifiers must be read-only, bounded/cancellable services and must tolerate a completed job when validating an exact completion replay. A timed-out verifier cannot commit an outcome through this ledger. Context and callback snapshots prevent caller mutation from changing a pending request, but do not freeze state hidden inside trusted callbacks.

Successful private derivative outcomes use `complete`; opt-in terminal no-output reconciliation is described below. Explicit retry generations are described below. Consumed work without authoritative final proof stays blocked. Guarantees are per job identity, not global deduplication of manager-created jobs. A host must not create a replacement job to bypass unresolved consumption. Before actual I/O the worker must also enforce its remaining runtime window and current policy; a permit consumed before expiry does not prove a lease remains valid after a delayed acknowledgement or that external permission cannot change.

## No-output reconciliation

`settleNoOutput(context, jobId, consumedRevision, proof, commandId)` adds a terminal `failed` state. Proof contains exactly a scoped receipt edition, a bounded failure reason, `processorStopped: true` and `noDerivative: true`. These fields are assertions until a trusted verifier validates them. A thrown exception, missing output observed at one instant or an expired lease is not proof that a processor cannot still complete.

A deployment may opt into `TextJobVerification.verifyNoOutput`; without it, reconciliation fails closed and old integrations retain their original behavior. The verifier receives the job, proof and exact consumed revision plus authenticated context and cancellation signal. It must establish final processor termination/quiescence and no committed or late derivative for that exact execution. Its strict true result is bounded by the existing verifier deadline. Workers can settle only their own purpose-bound execution; managers can reconcile scoped work.

Failure, exact receipt, immutable history, explicit audit event and outbox event commit atomically. Replay requires the same command and current identity/verification. `failed` cannot lease, consume, cancel or become successful, and creates no retry permit. An explicit manager operation may separately queue one successor as described below. Source bytes, diagnostics and exception strings are not stored. Eight new actual-migration/restricted-PGlite groups cover exact terminal receipts, missing/denied/invalid proof, current-authority replay, lost acknowledgements, rollback, timeout/late/nonboolean responses, success/failure races, stale revisions and captured manager recovery inputs. Final-head CI is recorded separately from local results.

`verifyNoOutput` is optional for backward-compatible construction, but mandatory for this operation. It must validate the original consumed revision on both new settlement and a `failed` replay. Old stored jobs require no migration: the `failure` field exists only on newly failed records. Consumers pinning this revision must handle the added terminal state explicitly. Existing successful outcomes cannot be overwritten by failure, and failed outcomes cannot later accept success; disputed/inconsistent external receipts require separate investigation. No receipt service, process liveness detector, or cross-service transaction is implemented here. Test verifiers are controlled fixtures, not evidence of a qualified production receipt service.

## Explicit retry lineage

`retryFailed(context, parentId, failedRevision, commandId)` is a listed-human-manager operation. It queues one deterministic child of an exact terminal failed edition only after freshly rechecking its stopped/no-output proof with `verifyNoOutput`. The verifier receives the original consumed revision (`failedRevision - 1`). Unresolved consumption, completion, cancellation and mere lease expiry do not permit retry. The child copies the parent's source edition/hash/byte count/language, purpose and processor profile; the caller cannot substitute an input. Each child carries its root ID, generation, exact parent failed revision and failure receipt. A lineage is capped at sixteen explicit retry generations.

The failed parent remains immutable. Atomic child creation, retry audit and queue outbox use the SDK project lock and expected-zero child insertion, so different managers or command IDs cannot produce a second child or reset one that has advanced. Exact command replay requires current manager authority and fresh proof verification and returns the original queued snapshot, even if the child has advanced. It is a historical queue acknowledgement, never permission to run. The child needs its own lease and fresh start authorization/consumption before I/O. No automatic retry, daemon or output dispatch is added.

Eight local restricted-migration groups cover lineage/source preservation, independent start checks, status/authority rejection, competing managers, lost acknowledgement, current proof/identity on replay, timeout/late results, callback/caller mutation, post-outbox rollback, deterministic-ID collisions and sixteen-generation bounds. One additional real PostgreSQL session group covers competing retry managers and replay after child consumption; final-head CI evidence is recorded in the PR. Production proof services remain unqualified. A deterministic successor enforces one child per parent edition, not global deduplication of separately submitted roots; hosts must still prevent bypass with replacement root IDs.

## Verifier deadline enforcement

All start, completion, no-output settlement and retry proof callbacks share a monotonic admission/result deadline as well as the cancellation timer. Blocking JavaScript past the deadline cannot win a delayed timer and authorize a ledger transition; exact cached command responses still need timely current verification. Only strict `true` passes. Callback failures, including their own DomainErrors, are sanitized, and every callback signal closes when verification exits, including success. Late asynchronous results cannot resume a timed-out operation.

PR14 reproduces all four blocked-result transitions on prior source and adds seven restricted-migration groups covering those transitions, cached response verification, late asynchronous results, sanitized diagnostics, nonboolean denial and signal cleanup. The complete 94-group ordinary local suite, typecheck/build/registry pass. All seven groups also pass through installed compiled public exports; final-head CI is recorded separately. No new network-session scenarios or real proof/identity/source services are qualified. The deadline cannot preempt blocked JavaScript, undo callback side effects or bound a database transaction already begun; trusted verifiers must remain read-only and independently qualified.
